## Core Phase 21K demo task dispatch and shard read model smoke fix

## Scope

- Added an immediate controlled demo task dispatch attempt after safe demo task creation.
- Reused the existing registered-worker selection and internal worker delivery path.
- Kept demo task submit constrained to `echo-api` with `echo-k6-smoke` or `echo-jmeter-smoke`.
- Returned a deterministic single-task shard read model for non-sharded controlled demo tasks.
- Kept result callback and artifact download protected.
- Did not add target apps, DB migrations, artifact download, report viewer, formal access system, or image startup migration.

## Changed Files

- `control-plane/apps/tasks/tasks.py`

- `docs/v3/runbooks/external-db-runtime.md`
- `docs/v3/runbooks/local-smoke-image-build.md`
- `docs/v3/changes/daily/2026-06-19.md`

## Summary

- Pending root cause: controlled demo task creation produced valid task rows, but API-only deployment smoke did not run Celery beat and therefore relied on later scheduled dispatch. If no compatible idle worker was selected, the task stayed `pending`.
- Core now attempts one immediate dispatch for smoke-created safe demo tasks. If no compatible idle worker is available, the task remains `pending` with a diagnostic `error_message` instead of being silently indistinguishable from an unprocessed task.
- When a compatible worker accepts delivery, the task transitions to `dispatched`; later `running`, `completed`, or `failed` transitions still depend on the existing worker result callback path.
- Non-sharded controlled demo tasks now return HTTP 200 shard metadata with `mode=single`, `shards=[]`, and `status=not_applicable`.
- Result summary and artifact metadata remain readable only for smoke-created safe demo tasks when the flag is enabled.
- Result callback, artifact download, unsafe profile submit, target override submit, and arbitrary task operation remain protected or blocked.
